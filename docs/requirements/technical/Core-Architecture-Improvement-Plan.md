## 1. Storage 提供通用内存状态机制

将通用状态容器及状态转换机制放在 Storage，采用进程内内存存储。各业务模块定义自己的状态、事件、合法转换和业务约束，通过显式接口使用 Storage 的机制。Storage 不集中管理全项目业务状态，也不决定设备操作、Agent 决策或 UI 流程。

- 提供类型化状态、一致快照、版本校验和原子转换，拒绝非法转换及过期写入；通用转换机制可接收业务拥有者提供的纯转换规则，外部副作用仍由业务拥有者执行。
- 每类状态明确唯一权威来源、隔离方式、所有者、有效期和清理条件。根级共享状态不随页面销毁；页面局部展示状态仍由 UI 管理。
- 异步副作用的接纳、执行和实际完成分别确认。取消或失败保留已发生的效果；设备目标、实际反馈和未知/过期状态分开表达，防止旧回调覆盖新会话。
- 为状态数量、载荷及订阅者定义上限和超限行为。若只发布最新状态，可合并完整快照；必须处理的事件不能静默丢弃。
- 进程重启重新取得事实，内存状态不承担持久化恢复或设备动作重放。

[Resource 当前状态存取计划](../Resource-State-Plan.md) 是本项的首个应用场景。该计划的快照存取与本项的状态转换机制共同设计；资源事实缓存不替代 Gateway 执行状态、资源锁或业务状态机的权威来源。

验收：合法/非法转换、并发版本冲突、取消与迟到回调、容量拒绝、状态失效，以及跨页面生命周期。

## 2. 错误分类与用户展示和开发日志分离

错误由实际发生的模块产生并保留原始原因；通过稳定的错误类别和代码传递。展示边界将同一错误分别投影为用户可读文案与开发者诊断信息，避免直接把原始异常描述作为 Toast。

| 内容 | 计划契约 |
| --- | --- |
| 分类 | 参数/配置、权限、能力或资源不可用、网络/服务、存储、超时、协议/数据、内部异常；业务模块保留领域子码。 |
| 用户 Toast | 简短、可理解、可本地化，说明发生了什么；只有存在有效恢复操作时才给出建议。未知错误也提供可读文案。 |
| 开发日志 | 保留错误类别/代码、原始原因链、失败阶段、模块、时间及实际可得的 session/input/call 等关联信息。明确诊断字段大小和截断标记，敏感数据脱敏。 |
| 取消与部分失败 | 正常取消作为终态，不当作异常 Toast；真实清理失败单独记录。部分完成保留成功步骤和各失败原因。 |
| 展示策略 | 错误事实与 Toast 生命周期独立；定义优先级、重复合并和关闭时机，防止旧会话异常覆盖新会话。 |

✅ 已有局部实现：识别错误展示“我没听清”，日志保留原始消息；播放边界存在保留 underlying error 的文案适配。❌ 全局分类、统一双层投影及一致展示策略仍待实现。参见 [App](../../../MobileHarness/App/README.md) 与 [既有错误语义](../../adr/0132-execution-error-semantics.md)。

领域错误语义属于各生产者；用户文案属于展示契约，UI 接收展示值；App 仅创建和连接接口，不持有全项目业务错误规则。错误分类本身不授权自动重试，也不将失败改写为成功。

验收：已知/未知错误文案、原始原因保留、关联信息、脱敏与截断、正常取消、部分失败，以及 Toast 替换与清理。

## 3. App 聚焦模块装配与生命周期

App 作为应用组合根，负责模块和服务的创建、能力加载与注册、依赖注入、启动停止、生命周期和资源清理，接口适配由业务拥有者的独立集成目标承担，App 不转换业务数据。业务决策归 Agents，业务操作归 Actions 或相应领域服务，展示与页面交互归 UI。梳理 App 中现有工作流，逐项区分必要宿主机制与应迁回业务拥有者的规则。

本轮目录与编译依赖整理提案见 [App 宿主职责与目录调整方案](App-Host-Boundaries-Plan.md)。✅ 纯组合根、集成编译边界、业务迁出及通用生命周期已实现；自动化与构建限制见实施计划和验证记录。真实模型/原生 UI/物理设备验收仍为 ❌。

服务管理使用显式契约和依赖顺序；定义加载/注册失败的传播、部分启动回滚、注销及停止完成语义。消费者通过注入接口使用能力，避免全局服务查找和隐式模块耦合。权限约束、即时原生停止及设备安全围栏由所属模块实现，App 只调用公开生命周期接口，长期任务不依赖页面寿命。

| 入口 | 计划路由与责任 |
| --- | --- |
| 用户点击的即时反馈、展开/选择、页面跳转 | UI 或注入的宿主能力直接处理，不经过 Action、Gateway 或 Agent 决策。反馈只确认交互被接纳，业务成功反馈等待真实结果。 |
| 用户提交业务操作 | UI 请求端口由 AgentBindings 适配，交给实际业务拥有者；保留该操作需要的权限、取消、执行和结果契约。 |
| Agent 发起的 UI 业务控制 | Gateway → Actions → ActionBindings → UI 公开能力；复用 UI 展示接口，保留执行身份、授权和完成语义。 |
| 生命周期、安全停止和清理 | App 调用所属服务的公开接口；服务执行必要的取消、等待与释放。 |

✅ 本地导航直接在 UI 完成，业务请求由实际 Agent 处理，Agent 发起的 UI 控制保留 Action 路径。App 不再持有业务适配器或领域工作流。参见 [App 当前路由](../../../MobileHarness/App/README.md#直接上下游)、[UI 交互契约](../../../MobileHarness/UI/README.md#interaction-and-acceptance) 和 [Actions 边界](../../../MobileHarness/Actions/README.md)。

验收：点击反馈及跳转直接完成、业务操作仍返回真实结果、Agent UI 控制权限与完成语义、启动失败清理、页面离开不终止根级任务，以及模块依赖检查。
