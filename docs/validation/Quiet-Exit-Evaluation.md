# quiet 退出判定评估（2026-11-23）

评估 Assistant 在 `listening=quiet` 时，仅凭用户最新一句话判断是否应退出 quiet 的能力。设计见[聆听模式](../requirements/technical/Listening-Mode-State.md)。这是 Python 模型实验，没有运行 App，也没有使用真机录音。

## 方法

- **用例**：[quiet-exit-cases-2026-11-23.json](../../experiments/decision/datasets/quiet-exit-cases-2026-11-23.json)，中英各半，手写。92 条计分（`exit` 36、`stay` 56），另有 6 条边界用例只记录不计分。`exit` 组：明确邀请、被叫（任意称呼）、想讨论或提问；`stay` 组：继续自己的叙述、对别人说话、自言自语、要求保持安静或延后、提到助手或转述邀请。
- **提示词**：[quiet-exit-prompts.json](../../experiments/decision/quiet-exit-prompts.json) 冻结了 App 判定通道的指令（中英各一）。生成式后端（Apple 系统模型、云端）与 App 相同：指令作 system，最新一句作 user，答 `exit` 或 `stay`，解析规则同 App。原生 Decision 模型（D3 Edge、Vela 3 Fast、Vela 3.1 Fast、Laya）不能回答单词，因此对同一指令使用实验专用的布尔问句形式，状态只含 `latest_user_sentence` 一个字段，概率 > 0.5 记为 `exit`。两种形式的措辞不同，对照时需要留意。
- **运行器**：[evaluate_quiet_exit.py](../../experiments/decision/evaluate_quiet_exit.py)，每个模型一次顺序运行，预热 2 条不计入，单条超时 60 s，采样参数由各后端默认或配置决定。标签不进入请求。离线回归 `python3 -m unittest discover -s experiments -p "test_*.py"` 通过（32 项）。
- **环境**：macOS 27.2.1 arm64，Python 3.13.13，coreai-core 1.0.0b3，apple-fm-sdk 0.2.2。Vela 3.1 使用 hugging-mac SDK 提交 `2e19add`，因为当前 main 已不含该模型模块。制品均按各清单固定版本下载并通过逐文件哈希校验；Laya 的 `_laya_host.py` 取自清单哈希对应的上游提交 `365a3045`，不是当前 main。

## 观察

- 没有模型同时做到低误唤醒和低漏退出。D3 与 Vela 偏向保持安静：几乎不误唤醒，但漏掉大半的邀请。Laya 相反，邀请与被叫识别最好，但对“要求安静”的 10 条全部答了 exit，对他人说话也大量误判。
- 所有模型对“讨论或提问”类退出都很弱（最好 3/8）。这类句子在语义上更像普通问句，只凭一句话难以区分是否对助手说。
- 云端 qwen3.8-flash 明显最好：0 次误唤醒，只漏退出 4 次。它的失误集中在英文：4 条 `exit` 被答成 `stay`，其中 3 条附带的理由与标签自相矛盾（如 `stay — you asked me to speak.`）。云端延迟约 3 秒（p95 约 7.4 秒，含一次 60 秒超时），比本地模型慢一到两个数量级，且受网络与服务端影响。
- Apple 系统模型的延迟约为本地 Decision 模型的 3 到 6 倍，准确率并不更高。
- 在 App 的设计里，误唤醒会让助手打断用户，漏退出只会让用户再说一遍。本评估没有按这种不对称给模型加权，也没有给出推荐。

## 提示词变体：是否要求唤醒（是/否）

按要求把提示词简化为一个是非问题：用户说这句话，是否在要求唤醒你、和你对话。提示词 [quiet-wake-prompts.json](../../experiments/decision/quiet-wake-prompts.json) 不再列出什么算邀请：生成式后端只回答 `true` 或 `false`，原生 Decision 模型读同一问句的布尔（noul）概率，大于 0.5 为 true。同一批用例、同一环境、同样每个模型运行一次，原始输出为 `quiet-wake-<模型>-2026-11-23.json`。云端这次没有超时，各模型均无无效回答或错误。

| 模型 | 准确率（原 → 新） | 误唤醒（原 → 新） | 漏退出（原 → 新） | p50 毫秒（新） |
| --- | --- | --- | --- | --- |
| D3 Edge | 0.717 → 0.630 | 0 → 0 | 26 → 34 / 36 | 112 |
| Vela 3 Fast | 0.717 → 0.663 | 5 → 5 | 21 → 26 / 36 | 153 |
| Vela 3.1 Fast | 0.685 → 0.630 | 6 → 3 | 23 → 31 / 36 | 126 |
| Laya Multilingual | 0.630 → 0.728 | 23 → 0 | 11 → 25 / 36 | 129 |
| Apple 系统模型 | 0.626 → 0.630 | 12 → 1 | 22 → 33 / 36 | 453 |
| 云端 qwen3.8-flash | 0.945 → 0.935 | 0 → 3 | 4 → 3 / 36（原为 35） | 2219 |

- 简化问句让多数本地模型和 Apple 更保守：误唤醒大幅下降，但漏退出上升到 31 至 34 条，邀请类和被叫类几乎答不出。D3 的邀请组只有 1/16。
- Laya 受益最大：误唤醒 23 降到 0，“要求安静”组由 0/10 变为 10/10，总体准确率从最低升到本地最高；代价是漏退出增多。
- 云端基本持平，英文漏退出略少，但出现 3 次误唤醒；两种问法的差异在单次运行的波动范围内，不能判定谁更好。
- 本变体与原提示词同时改了问句措辞、去掉了对“什么算邀请”的说明和输出格式，无法区分各因素的影响；单次运行，每组样本很小。

## 提示词变体：最短问句，以及中英分开统计

最短问句 [quiet-wake-short-prompts.json](../../experiments/decision/quiet-wake-short-prompts.json)：生成式后端只收到一条 user 消息（无 system）：英文 `You are in quiet listening mode. The user said "…". Is the user asking you to wake up? Answer true or false.`，中文 `你现在处于安静聆听模式，用户说“…”，请问用户是否要求唤醒你，回答 true/false`。原生 Decision 模型读同一问句的布尔概率，句子放在状态字段里。原始输出 `quiet-wake-short-<模型>-2026-11-23.json`，无无效回答或错误。

三种提示词按语言分开（中文 / 英文，各 46 条计分：`stay` 28、`exit` 18；Apple 中文有 1 条护栏拒绝，Qwen 原提示中文 `exit` 为 17）。格式：准确率，误唤醒/28，漏退出/18。

| Vela 3.1 Fast | 0.61, 3, 15 | 0.76, 3, 8 | 0.61, 3, 15 | 0.65, 0, 16 | 0.61, 0, 18 | 0.63, 0, 17 |
| Laya | 0.59, 17, 2 | 0.67, 6, 9 | 0.76, 0, 11 | 0.70, 0, 14 | 0.72, 2, 11 | 0.67, 1, 14 |
| Apple 系统模型 | 0.69, 6, 8 | 0.57, 6, 14 | 0.65, 1, 15 | 0.61, 0, 18 | 0.72, 0, 13 | 0.61, 0, 18 |

总体（中英合计）最短问句：D3 0.652、Vela 3 0.620、Vela 3.1 0.620、Laya 0.696、Apple 0.663、云端 0.870（误唤醒 2、漏退出 10）。

- 本地模型和 Apple 在最短问句下几乎全部答 false，漏退出 25 至 35 条（共 36），实际上退化成“永不唤醒”。Vela 两个版本漏掉 35/36。
- 云端受影响最大且集中在英文：中文 0.96，英文降到 0.78（漏退出 8）。原提示词与“是否要求唤醒”问句在英文上都是 0.89 至 0.93，说明去掉系统指令与角色说明对英文伤害明显；中文几乎不受影响。
- 除 D3、Vela 在原提示词下英文明显好于中文外，其余模型没有统一的语言规律；原提示词下 Laya 中文误唤醒 17/28，英文 6/28，是最大的语言差异。
- 各提示词同时改了多个因素，单次运行，每语言每组样本很小，差异不应过度解读。

## Qwen3.5-0.8B（本地 Core AI）：未能完成评估

按要求接入 [mlboydaisuke/qwen3.5-0.8B-CoreAI](https://huggingface.co/mlboydaisuke/qwen3.5-0.8B-CoreAI)（修订 `8440bd88`，Apache-2.0），只做逐个顺序请求。制品已按固定修订下载到 `Models/Qwen3.5-0.8B`，`main.mlirb` 的 SHA-256 与仓库 LFS 记录一致，清单见 [models.json](../../experiments/decision/benchmark/models.json) 的 `qwen3.5-0.8b`（`gpu-pipelined-b2` 与 `macos` 两个变体）。没有产生评估结果文件。

本机（Apple M5，16 GB，macOS 27.2.1，coreai-core 1.0.0b3）上经共享的 `utils/coreai_decoder.py` 的结论：

- `context_length` 为 1024 时 GPU 报 `Insufficient Memory` 并输出乱码；`macos` 变体在 GPU 与 CPU 上也报错。
- 将 `context_length` 降到 64 至 128 后，`gpu-pipelined-b2` 变体可以正确解码（`The capital of France is` → ` Paris.\n`）。
- 之后又用 `context_length` 64 至 128 重测了 `macos` 变体（单图）：第一个 5 token 提示可正确解码（` Paris.`，首次 2 秒，重复 0.2 秒），但同一进程里接着处理更长的提示时，GPU 连续报 `Insufficient Memory`，输出变成 `capital!` 等乱码。每个新的 `position_ids` 长度都会触发重新特化，已特化的图看起来没有被释放。两个变体因此表现一致，`macos` 并不更好。
- 但该图的序列长度是动态的，每个未见过的长度都要重新特化：首次约 10 秒，同一进程内同长度之后只需不到 1 秒，不跨进程保留。模型卡与相关说明也提到该系列的 KV 写入需要特殊运行时。
- 用最短问句（约 50 个 token）完整运行时，这些逐长度特化使磁盘在数分钟内从约 76 GB 空闲耗尽到 0，进程随即崩溃（原始 exit/stay 提示词与“是否唤醒”提示词本身超过 128 token 的上下文）。两次尝试都因此中止，已清理残留文件，磁盘恢复。

因此当前不能在不占满磁盘的前提下用该解码路径完成 98 条评估，我没有保留配置文件。可行的方向是使用模型卡所述的 pipelined 运行时（需要 Swift 补丁，不属于 Python 实验），或固定序列长度的导出；这些都需要另外确认。

## 限制

- 用例是单人手写的 98 条短句（含 6 条不计分），覆盖面和措辞分布有限，没有真实 ASR 文本（含识别错误、口语停顿、更长的句子）。每个模型只运行一次，没有重复和置信区间，小组（8 到 16 条）的差异不应过度解读。
- 生成式与原生 Decision 模型的提示形式不同（见方法），差异混有提示形式的影响。没有做提示词变体对照。
- 延迟是单进程顺序运行、已预热的原生调用，不含 App 的调度、网络与模型加载，不能代表 App 内的端到端耗时。Apple 与云端走的 Python 接口与 App 的 Swift 调用不同。
- 云端 qwen3.8-flash 通过仓库外的 `.env.local` 取得接口地址与密钥（不入库、不进结果），请求选项见 [quiet-cloud-model.json](../../experiments/decision/quiet-cloud-model.json)（`temperature` 0、`max_tokens` 32）。运行用的配置是同一内容、仅 endpoint 与密钥变量名不同的本地临时文件，结果中的 `configSHA256` 对应该临时文件。接口是账号专属的兼容接口，未核对模型版本字符串对应的具体快照。
- 这些是 Python 实验结果，不是 App 内的验收；App 当前的判定通道只使用 Apple 系统模型与 Assistant 所选模型，不使用 D3、Vela、Laya。
